# First real AWS deploy of the v5 components

2026-10-01, in a lab account, region `us-west-2`, with `dist/sst5` built from `v5` at `64e9108ef` plus the fixes described below.

Until this run, every port had only been checked under a mock of the deploy engine.

## What it set out to answer

1. Does switching a deployed 4.x component to its v5 port keep what's in AWS?
2. Does a v5 stack work: endpoints, links, event sources?
3. Does `sst remove` take a v5 stack down cleanly, in order?
4. Does a stack created by v5 alone, with no 4.x in its history, deploy and remove?

## The test app

One app, one stage, three groups. Each group's code is typed against `sst.aws.v5` and can be run with the 4.x components or the v5 ones, which is the same as changing `sst.aws.X` to `sst.aws.v5.X` on every component in it. The config type-checked against the v5 types as written.

| Group | What's in it |
| --- | --- |
| Serverless | `Bucket` with a notification to a function. `Queue` with a dead-letter queue and a subscriber. `SnsTopic` with a function subscriber and a queue subscriber. `Dynamo` with a stream subscriber. `CognitoUserPool` with a trigger and a client. `Function` with a URL and six links. `ApiGatewayV2` with a custom domain, three routes and a Lambda authorizer. `AppSync` with a Lambda data source and a resolver. `CronV2` with a function. |
| Containers | A 4.x `Vpc` (not ported). `Cluster`. `Efs`. `Service` with its own load balancer, custom domain, redirect rule, scaling, Cloud Map and an EFS volume, its image built from a Dockerfile. `Alb` with a custom domain and two listeners. A second `Service` on that `Alb`. `Task`. `CronV2` running the task. A `Function` in the VPC that mounts the file system and links the task, the `Alb` and the service. |
| Databases | `Postgres` with a proxy. `Mysql`. `Redis`. `Aurora`. `Dsql` with VPC endpoints. A `Function` in the VPC that links all five. |

Each step was checked three ways: `sst diff` before the deploy, the exported state before and after compared by resource type and id, and calls to what was deployed (URLs, routes with and without the authorizer's token, an upload, a publish and a table write followed through to each subscriber's logs, a file written on EFS, the properties of each database's link).

## Results

| Step | Result |
| --- | --- |
| Serverless: deploy with 4.x, switch to v5 | The diff showed the 4.x wrapper components going and the eleven renamed functions updated in place (code uploaded under the new name, four descriptions). Every AWS resource kept its id, 73 of them under a new name. Only the eleven code objects were replaced. |
| Containers and databases: deploy with 4.x (311 resources), switch to v5 | The diff showed nothing changing in AWS: two `sst dev` commands moving and three 4.x version markers going, all in the state. All 238 AWS resources kept their ids. The EFS file kept its contents. |
| After the switch | Every endpoint, link and event path worked. A second diff reported no changes. In the state, each load balancer now depends on its certificate. |
| Remove the switched stage | 284 resources deleted, no errors, about 45 minutes. |
| Deploy serverless and containers with v5 only | 236 resources created, all working, including a subscriber that links its own queue and a route that links its own API. |
| Remove that stage | 236 resources deleted, no errors. |

## What it found

Three bugs in v5 that every test under the mock had passed, each now fixed and covered by a test.

### 1. The takeover maps weren't in a real build

The first diff after a switch showed everything that had moved as deleted and created.

`platform/package.json` said the package has no side effects. The CLI bundles a config with esbuild, which then leaves out a file that's imported for what it does and not for what it exports. Every takeover map is such a file, so no alias reached the engine. Under the mock nothing is bundled.

**Fix:** `"sideEffects": ["./src/components/aws/takeover/*.ts"]`. `v5-components.test.ts` now bundles the components the way `pkg/js/js.go` does and checks every map is in the output.

### 2. A function's links were written into its code under one garbage key

A function with links got different code under v5 even with its name unchanged. Decrypting the two payloads showed why: v5 wrote all the links under a single key, the text of Pulumi's "calling toString on an Output" warning. `Resource.X` would have failed in every v5 function with links.

The v5 `Function` read its links with `.apply()` over an array of outputs. 4.x wraps the same value in `output()`, which unwraps what's inside. A function's links go into its code, not into any resource's inputs, so no comparison of inputs could see it.

**Fix:** the links are read with `all()`. The mock now records what each function is built from (handler, runtime, copied files, properties, links) and the takeover check compares it. That reproduced the bug in six existing cases before the fix.

### 3. A function part that links its own component was never created

Found by comparing the dependencies in the real 4.x and v5 states: a v5 function's code depended on every resource of every component it links.

A link's name is read from the linked component's `urn`, and depending on a component is depending on everything in it. A function part is inside its component, so one that links that component (`queue.subscribe({ handler, link: [queue] })`, a route that links its API) waited for itself. It was never created, and nothing reported an error. 4.x didn't have the problem only because its subscriber sat outside the queue.

**Fix:** `withoutDependencies()`, new in `args.ts` and built the way Pulumi's own `unsecret()` is. The build result is passed through it, so the code depends on nothing, as in 4.x. The permissions and environment still carry the dependencies the function needs.

### Not v5's: `Mysql`'s default version is gone

RDS no longer offers MySQL `8.0.40`, the default of both the 4.x and the v5 `Mysql`. A `Mysql` with no `version` fails to create. The test passed `8.0.46`. Not changed in the components; see Open questions in the plan.

## What a removal leaves behind

The same under 4.x, and none of it running:

- The RDS proxy's own log group, `/aws/rds/proxy/<name>`. AWS creates it, so SST never knew about it.
- Function sourcemaps in SST's asset bucket, kept on purpose (`retainOnDelete`).
- The build-cache image of a service's container in SST's `sst-asset` repository.
- Deregistered ECS task definitions, which ECS keeps as inactive.
- SST's own records of the stage: its passphrase in SSM and its files in the state bucket.

The AWS tagging API goes on listing deleted resources for a while. Check a resource directly before believing it's still there.

## Things worth knowing next time

- **A removal is slow.** The two ECS services drained one after the other, about seven minutes each, and RDS, the proxy, Aurora and Redis each took several more.
- A new API Gateway domain, and DNS that was just recreated, need a minute or two before they answer.
- A function's log group isn't named after the function: read it from the function's logging config.
- `sst state export` before and after, compared by resource type and id, is the definitive check that nothing was replaced.

## `sst dev`, later the same night

The serverless group, created by v5 alone, was run under `sst dev --mode=basic`.

- Each function was deployed as the live stub (`bootstrap` on `provided.al2023`).
- A call to a function's URL, a call to an API route, a publish to the topic, and the message the topic passed on to the queue were each run on the local machine, and the function with six links read all of them.
- A handler edited while it was running was picked up on the next call, with no deploy.
- The stage was removed afterwards with no errors.

Not looked at: a `Service` or `Task` under `sst dev`, the multiplexer's panes, and `sst dev` on a stage that was deployed with 4.x.

One thing to look at again: that deploy took 18 minutes and its removal 24, though no single resource took more than a minute. In the CLI's log the time went into two long pauses between pushes of state to S3 and one 15-minute pause in the clean-up of the stage's event log folder. The credentials expired before it could be looked into, so whether it was the network that night or something in the CLI isn't known. It isn't in a component.
