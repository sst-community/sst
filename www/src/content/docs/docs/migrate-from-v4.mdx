---
title: Migrate From v4
description: Rewrite your config for SST 5's components with the codemod, then move each stage with sst migrate, keeping what you've deployed.
---

SST 5 rebuilds SST's components on one foundation. [Why SST 5](/docs/why-sst-5/) says what that changes for your app, and what it costs. You move an app in two steps: the codemod rewrites your config for the new components, then `sst migrate` moves each stage to them in one deploy. What you've deployed is kept. The move is checked first, and it stops before it would delete or replace anything that holds data.

:::caution
SST 5 is in pre-release. Its components can still change in any way before 5.0.0, so move a stage of its own first.
:::

:::note
On SST 2 or SST 3? Move to SST 4 first, with SST 4's guides: [from v2](/sst/docs/migrate-from-v2/) to SST 3, then [from v3](/sst/docs/migrate-from-v3/) to SST 4.
:::

In short:

1. [Get ready](#before-you-start) on SST 4.
2. [Install SST 5](#install-sst-5).
3. [Rewrite your config](#rewrite-your-config) with `sst migrate --codemod`.
4. [Check a stage](#check-a-stage) with `sst migrate --check`.
5. [Move it](#move-a-stage) with `sst migrate`, and confirm with `sst diff`.

Then the next stage: a dev stage first, and production last.

---

## What changes

- **The components are new.** They take the place of SST 4's, as `sst.aws.*`, `sst.cloudflare.*` and `sst.x.*`, and three of them have clearer names.
- **Each has the same type as the one it replaces**, `sst:aws:Queue` for both queues. So what links to it sees no change, `Resource.MyQueue.type` stays the same, and a `$transform` for either applies to both.
- **A few have new names**, with the same type:

  | SST 4 | SST 5 |
  | --- | --- |
  | `sst.aws.ApiGatewayV1` | `sst.aws.ApiGatewayRest` |
  | `sst.aws.ApiGatewayV2` | `sst.aws.ApiGatewayHttp` |
  | `sst.cloudflare.StaticSiteV2` | `sst.cloudflare.StaticSite` |

- **A stage moves once, and whole.** SST 5 doesn't deploy SST 4's components. On a stage deployed with SST 4, `sst deploy`, `sst dev` and `sst remove` are refused until it has moved; `sst diff` and `sst refresh` still run. To remove a stage you won't move, like an old preview stage, use SST 4, as the branch it was deployed from does. A new stage is refused SST 4's components too.
- **The move keeps what's deployed.** Each component knows which of SST 4's resources each of its own takes the place of, and the move carries them over under their new names. A resource that can't be carried over, like a site's uploaded files, is let go without being deleted, and what takes its place writes the same thing again.

## Before you start

1. **Every component you use has to have a 5.0 form.** These don't. Deal with each one with SST 4 and deploy, before you move a stage that has it. `sst migrate --check` reads the stage's state and names each one it has, so you don't have to look for them. The codemod can't always tell from your config: Cloudflare's first `StaticSite` is written the way its 5.0 form is.

   | Component | What to do |
   | --- | --- |
   | `sst.aws.Vector` | Move its vectors to a vector database of their own, then remove it. |
   | `sst.aws.OpenControl` | Remove it, and run OpenControl outside of SST. |
   | `sst.aws.Auth.v1` | Move to `sst.aws.Auth`, OpenAuth's. |
   | `.v1` of `Vpc`, `Cluster`, `Postgres` and `Redis` | Move to the component's current version. |
   | `sst.cloudflare.StaticSite`, the first one | Move to `sst.cloudflare.StaticSiteV2`, which is `StaticSite` in 5.0. |
   | `sst.cloudflare.Auth` and `sst.cloudflare.x.SolidStart` | Remove them, or keep the stage on SST 4. |

2. **Update to the latest SST 4 and deploy**, from where you'll move the stage, with nothing changed in between. Then what SST 4 changed since your version is deployed on its own, and not with the move. SST 4 keeps the full path of the folder a container's image is built from, so from another folder, like your CI's, or with the image's files changed, the image is built again and its task definition is replaced, and `sst migrate --check` refuses a move that replaces it.

3. **Use Node.js 22 or later.**

4. **Check your `sst.config.ts`** for the four things SST 5 reads differently. Most apps have none of them.

   - **A `version` rule has to allow 5.x.** An app without one runs with any version.

     ```ts title="sst.config.ts" del={5} ins={6}
     export default $config({
       app(input) {
         return {
           name: "my-app",
           version: "4.x",
           version: ">= 4",
         };
       },
     });
     ```

     | Rule | SST 4 | SST 5 |
     | --- | --- | --- |
     | No `version` | ✓ | ✓ |
     | `"4.x"` or `"^4"` | ✓ | |
     | `">= 4"` | ✓ | ✓ |
     | `"5.x"` | | ✓ |

   - **A provider pinned to a version** has to be in the major version SST's components are built for, like `aws` `7.x`. A newer major version is refused too, and the error gives the versions to use.

   - **A file that re-exports a global by name**, like `export { aws }`, no longer builds. `export const x = aws` and `export default aws` work.

   - **A file that `app()` imports can't use a provider while it loads.** Providers aren't installed yet when `app()` runs, so a provider there is a stub that throws when it's used.

5. **Commit your changes.** The codemod leaves a file with changes git hasn't committed as it is, so that what it changes shows as a diff.

## Install SST 5

In your app:

```bash frame="none"
npm install sst@npm:@sst-community/sst@next-experimental
```

Or, for an app that isn't JavaScript, install the CLI globally, with `VERSION` set to the pre-release's version from the [releases page](https://github.com/sst-community/sst/releases). This replaces a global SST 4 CLI.

```bash frame="none"
curl -fsSL https://raw.githubusercontent.com/sst-community/sst/main/install | VERSION=<version> bash
```

## Rewrite your config

The codemod rewrites your `sst.config.ts`, and the files it imports, for the new components. It needs no stage and no credentials. Run it with `--dry-run` first, to see the diff without writing anything:

```bash frame="none"
sst migrate --codemod --dry-run
sst migrate --codemod
```

It makes the changes that are mechanical:

- **The names**: the three renamed components get their new names, wherever they're written, in a `new`, a `get`, a type or a `$transform`. A name the v5 alphas wrote, like `sst.aws.v5.Queue`, loses its `v5`.
- **The args written differently**, like a function's `role`, which is `existing.role`, a service's `public`, which is `loadBalancer`, or a site's `route`, which is `router`. Args that SST 4 ignored, and SST 5 refuses, are removed, and it says where they go if you meant them.
- **What a method gave.** A route, a subscriber or a data source isn't a component of its own any more. So a read like `subscriber.nodes.function` becomes the component's, `bus.nodes.subscriber["MySubscriber"]`, and a subscriber's own `transform` moves into the component's `transform`, for that subscriber only.
- **The static methods that took an ARN**, which are methods of what `get` gives: `sst.aws.Bus.subscribe(name, arn, ...)` becomes `sst.aws.Bus.get("MyBus", arn).subscribe(name, ...)`.

It lists each change, and each thing it couldn't do, marked `!`, with what to write:

```txt frame="none"
✓  sst.config.ts:9   `sst.aws.ApiGatewayV2` is `sst.aws.ApiGatewayHttp`
✓  sst.config.ts:11  `Bus`'s `subscribe`'s `transform.rule` is the bus's `transform.rule`, for its id
✓  sst.config.ts:18  `Service`'s `public` is `loadBalancer`, with the same settings
!  sst.config.ts:25  `Router`'s `routes` are gone. With SST 4, add each with `route()` or `routeBucket()` in place of `routes` and deploy; then move the stage.

3 changes, and 1 thing to do by hand, marked !. Then run `sst migrate --check` on a stage.
```

Do what it lists, then run it again: it changes nothing a second time. Some of what it lists has to be done with SST 4 and deployed before the stage can move, like a `Router`'s `routes` or a subscriber without a name. It doesn't change a package's components, or anything in `node_modules`.

Where the codemod wasn't run, or couldn't read the code, SST 4's names fail with what to write:
- a component's name, like `new sst.aws.ApiGatewayV2(...)`, which says it's `sst.aws.ApiGatewayHttp`, in a `new`, a `get`, a `$transform` or `sst.Linkable.wrap`;
- a `.v1`, like `sst.aws.Vpc.v1`, and `sst.linkable`;
- a `nodes` name SST 5 renamed, like `vpc.nodes.privateSubnets`, which says to read `nodes.privateSubnet`, and a subscriber's or a route's function read on what `subscribe` or `route` gave, like `subscriber.nodes.function`, which is the component's `nodes.subscriber` in SST 5;
- the other `nodes` of what `subscribe`, `route` or `addResolver` gave, read as one resource, like `subscriber.nodes.rule.arn`: SST 5's `subscribe` gives the component, whose `nodes.rule` has a rule for each subscriber, by its name, so it says to read `nodes.rule["MySubscriber"].arn`. The same goes for a site's `nodes.server.url`, and for any record by id read as one of its resources;
- `nodes` read on what `addAuthorizer`, `addDataSource`, `addFunction` and `addIdentityProvider` give, which is the resource in SST 5, like `authorizer.nodes.authorizer`, which says to read the authorizer's own fields.

Some reads fail without saying so, so look for them where the codemod wasn't run:
- a record by id passed on whole where SST 4 gave one resource, like `subscriber.nodes.rule` given to another resource's args, which isn't read as one of them;
- a field read on a record with nothing in it yet, like `bus.nodes.rule.arn` before the bus has a subscriber, which is `undefined`;
- a check written to tell SST 4 from SST 5 by whether a name exists, like `sst.aws.ApiGatewayV2 ?? sst.aws.ApiGatewayHttp`, which finds SST 4's name in SST 5 too.

### What the codemod can't see

A few changes depend on what your values are, not on how they're written. Look for these yourself:

- **Args that decide what gets created are plain values, not outputs.** `sst diff`, `sst migrate --check` and a deploy refuse an output there, with the arg's name and why. Only the arg itself has to be plain: what's inside it can be an output, and so can most args, like `link`, `environment` or a `vpc`. Each component's docs say which args. For a value from a lookup, like a domain from a hosted zone, `await` the lookup in `run()`, which gives a plain value: `const zone = await aws.route53.getZone({ zoneId: "Z123" });`.
- **`nodes` has every resource a component creates**, and each is the resource itself, not an output of it. A read of one, like `fn.nodes.function.name`, works as it did. Where SST 4 gave an output and you called `.apply()` on it, the codemod wraps it in `$output()`, which keeps a resource as it is; or read it directly, as `router.nodes.cdn.nodes.distribution.arn`. A site's `nodes.server` is a record by region, and SST 4's was the first region's: the codemod writes `Object.values(site.nodes.server)[0]`. A static `Astro` site's, and a `React` site's in SPA mode, is `undefined`, as SST 4's was. A function a component creates for each route, subscriber or region is still an output. Some may be `undefined`, like a service's `nodes.autoScalingTarget`, and each component's docs say which.
- **A domain's `dns` is one of SST 5's adapters.** `sst.aws.dns()`, `sst.cloudflare.dns()` and `sst.vercel.dns()` work as they did. An object written by hand for SST 4's components, with `createRecord`, `createAlias` and `createCaa`, is refused, as SST 5's components call `record`, `alias` and `caa`. To write one for another provider, implement `DnsAdapter` from `sst/components`.
- **An object in `transform` is merged in**, nested objects too. SST 4 replaced the nested object it named, without SST's settings in it, like a function's `loggingConfig` without its log group. Where that changes what's deployed, `sst migrate --check` says so under the resource it changes, with the settings the merge keeps. To replace one as SST 4 did, use a function. A setting the object gives as `undefined` is unset, as it was in SST 4. Where AWS won't take both, like an OpenSearch master user given by its ARN beside SST's username and password, the move's deploy fails on it, so check what `--check` lists.

  ```ts title="sst.config.ts"
  transform: {
    // SST 4 replaced every variable, SST 5 adds A
    function: { environment: { variables: { A: "1" } } },
  }
  ```

- **A `transform` function can be given outputs** where SST 4 gave plain values: for what's only known once the deploy runs, like a `Vpc` subnet's `availabilityZone` when `az` is a number, or a `Task`'s container definitions, and for what follows from an arg you set as an output, which SST 4 resolved first. Otherwise it's given what SST 4 gave it, an output where SST 4 gave one, like a function's `timeout`, and a plain value where SST 4 gave one, like a table's `hashKey`. Each component's docs list what's different. For a part a component has several of, like a route or a subscriber, it's called for each one, with its id last. What it changes in the args is a copy, as it was in SST 4: it doesn't reach your config.

## Check a stage

`sst migrate --check` previews the move of a stage and changes nothing:

```bash frame="none"
sst migrate --check --stage dev
```

It shows what the move keeps, what it carries over to a new name, and what it updates in place. It fails if the move would:

- delete or replace anything that holds data, like a bucket, a table, a database or a log group;
- create, delete or replace anything the components don't say they take the place of.

Expect updates in place, like a function's description or the tags SST sets. A few things are expected to change more:

- **A function whose part has a new name uploads its code again.** The function is updated in place. A `Cron`'s or a `CronV2`'s function is one: it was `MyCronJobHandler` and is `MyCronJobFunction`.
- **A file uploaded under a key made from what's in it**, like a function's code or a site's build, is replaced when what's in it changes, as on any deploy.
- **Nothing is replaced for a change of provider alone.** SST 4 created some resources with your app's provider, whatever the component was given, like the queue subscribers of a `Bus`. A 5.0 component gives each one its own `provider`, and the move keeps them, updated in place.

For a stage you deploy with `sst dev`, check it the way `sst dev` deploys it, with a stub in place of each function:

```bash frame="none"
sst migrate --check --dev --stage dev
```

## Move a stage

When the check passes, move the stage:

```bash frame="none"
sst migrate --stage dev
```

Move a stage you deploy with `sst dev` the way you checked it, with `--dev`, so it keeps a stub in place of each function. Without it, the move would put each function's code in place of its stub, and the check refuses that:

```bash frame="none"
sst migrate --dev --stage dev
```

It takes the stage's lock, checks the move again, and stops there if the check fails. Then it saves a copy of the stage's state in your app's home, takes out of the state what the components let go of, without deleting it, and deploys, with a preview first. It holds the lock from the check to the end, so nothing else deploys the stage in between. The deploy runs your config again, so don't change it while the move runs, or what it deploys isn't what it checked.

Then confirm. `sst diff` should show nothing to create or destroy:

```bash frame="none"
sst diff --stage dev
```

From then on, the stage deploys with `sst deploy` and `sst dev` as before. Move the next stage the same way, with production last.

:::danger
Don't deploy a stage that has moved with SST 4, like from an old branch or in CI. It would try to put back SST 4's resources in place of what moved.

SST 5 keeps a lock on a stage that has moved, where SST 4 looks for one, so SST 4's `sst deploy`, `sst dev`, `sst refresh` and `sst remove` stop with "A concurrent update was detected". **Don't run SST 4's `sst unlock` on it**, except to [go back](#going-back) with the state copied back first: it takes the lock out, and SST 4 would then deploy. SST 5's `sst unlock` leaves it. SST 4's `sst state` commands don't take the lock, so don't run them on a stage that has moved either.
:::

Set a `version` rule, so that anyone on SST 4 is told their version doesn't match, before the config runs:

```ts title="sst.config.ts"
version: "5.x",
```

## If you wrote a package

A [package component](/docs/write-a-package-component/) built on the v5 alphas, up to `5.0.0-alpha.2`, works on 5.0 with a few changes. The rest of what it imports from `sst/components`, `sst/components/aws` and `sst/testing` is the same.

- **SST's components aren't in `v5` any more:** `v5.Queue` from `sst/components/aws` is `Queue`, and `sst.aws.v5.Queue` in an example is `sst.aws.Queue`.

- **One of SST's components has a new name**, with the same type, so what an app deployed with it is kept: `v5.ApiGatewayV2` is `ApiGatewayHttp`, and its types are `ApiGatewayHttpArgs`, `ApiGatewayHttpAuthorizerArgs` and `ApiGatewayHttpRouteArgs`.
- **Two args are gone:** `Redis`'s `nodes`, which is `cluster.nodes`, and `Cluster`'s `forceUpgrade`.
- **`linkable` is gone** from `sst/components`. Use `Linkable.wrap`. `V5Args`, which wrapped a v4 component's args, is gone too.
- **Drop `skipLibCheck` and the `google-protobuf` pin.** SST's types check without `skipLibCheck`, under `moduleResolution: "bundler"` or `"NodeNext"`, and `mock()` works with the `google-protobuf` that `@pulumi/pulumi` installs.
- **`mock()` answers more as the cloud would.** An `Email`'s domain gets three DKIM tokens, so a test that gave them in `state` doesn't have to.

Then there's what a package can do now that it couldn't:

- **Read the app with `context()`**: its name, stage, removal and providers, whether it runs for `sst dev`, the command, and the stage's target.
- **Version a component**, so that renaming its parts moves an app's stage with `sst migrate` instead of replacing what's deployed. Give the component its next version with `takeover()`, and say where each part was.
- **Export a check**, made with `check()`, that an app turns on in `run()`. A deploy runs a preview first and stops on what the check finds.
- **Export a runtime**, made with `runtime()`, for a language SST doesn't build in, or **a target**, of the `Target` type, which `targetSuite()` from `sst/testing` tests.

From 5.0 on, what a package builds on changes only in a major version.

## Going back

You can put a stage that has moved back on SST 4, as long as nothing else has been deployed to it with SST 5. Going back takes three things from before the move: your config, SST 4, and the stage's state. Git has the first two, if you committed before the codemod, as [Before you start](#before-you-start) says. The move saved the third.

1. **Check out the commit from before the codemod**, and install. It has SST 4 in your `package.json` and lockfile. With a global CLI, install SST 4 again.

2. **Copy the saved state over the stage's state.** In your app's home, the copy is at `migrate/<app>/<stage>/<id>.json`, the newest one if you moved the stage more than once, and the stage's state is at `app/<app>/<stage>.json`. On AWS, the home is your account's SST state bucket, named in the SSM parameter `/sst/bootstrap`:

   ```bash frame="none"
   aws s3 cp s3://<bucket>/migrate/<app>/<stage>/<id>.json s3://<bucket>/app/<app>/<stage>.json
   ```

3. **Take out the lock** SST 5 keeps for SST 4, with SST 4's `sst unlock`.

4. **Deploy with SST 4**:

   ```bash frame="none"
   sst deploy --stage dev
   ```

:::danger
Copy the state back before you run SST 4's `sst unlock`. Without it, SST 4 reads SST 5's state, where much of what moved has a new address. SST 4 doesn't know those addresses, so it tries to create each of those resources again, and to delete the one at the new address, with what's in it. In a test of an app with an API, functions, queues, a table, a bucket and a user pool, that was 86 of its 117 resources, 13 log groups among them, with their logs; the table, the bucket, the queues and the user pool kept their addresses. In a test of SST's databases, Postgres, MySQL, Aurora, Redis and DSQL kept theirs, and their secrets in Secrets Manager moved.
:::

This was tried with SST 4.24.0: on the app above with an API, deployed once with `sst deploy` and once with `sst dev`, on SST's databases, on a router with SST's sites behind it, on SST's containers, and on Cloudflare's components with their sites. Each time, SST 4 deployed the stage, changing nothing but what a build changes, and later removed it. But the copy is the state from before the move, and the move changed some things in place. It uploaded each function's code again, which stays in your asset bucket unused, and updated some functions. SST 4 compares your config with the copy, not with what's deployed, so those functions keep what SST 5 gave them until SST 4 changes them. Two of those can matter, both for a function the move gave a new name, like a subscriber or an API's route:

- **On a stage you use with `sst dev`,** the function keeps the name SST 5's `sst dev` knows it by, so SST 4's `sst dev` doesn't reach it, and calls to it fail. Run SST 4's `sst deploy`, then `sst dev`.
- **A function whose code is a `bundle`,** like a Next.js site's, reads its links from a file named after it, so it looks for the file under its new name. Run SST 4's `sst refresh`, then `sst deploy`.

SST 4's `sst refresh` can fail after going back, with "cannot complete a resource … whose registration isn't pending". The move deleted the code SST 4 had uploaded for each function it gave a new name, the ones `sst migrate --check` said upload their code again. SST 4's state still names that code, as `<function>Code` under SST 4's name for the function, and SST 4's deploy doesn't upload it again. Its refresh then fails on a component linked to one of them, like a user pool with a trigger. Take each of those out of SST 4's state, then deploy, and SST 4 uploads them again:

```bash frame="none"
sst state remove UsersTriggerpreSignUpCode --stage dev
sst deploy --stage dev
```

In the tests, the refresh failed this way for the app with the API, and passed for the others. So go back only to get a stage onto SST 4 again quickly, and move it again when you can.

Once the stage has been deployed again with SST 5, the copy no longer matches what's deployed. Fix forward instead.
