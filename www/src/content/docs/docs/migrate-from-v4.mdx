---
title: Migrate From v4
description: Move your SST v4 app to v5, then switch its components one at a time.
---

v5 rebuilds SST's components on one foundation. It still has the v4 components, so you move an app in two steps:

1. **Install v5.** Your config keeps working as it is, and deploys what it deployed with v4.
2. **Switch components to `sst.aws.v5.*`**, one at a time, when you want to. Each switch keeps what you've deployed.

:::caution
v5 is in pre-release. Its components can still change in any way before 5.0.0, so try it on a stage of its own first.
:::

---

## What changes

- **The CLI is 5.x.** Everything in `sst.aws.*` is still the v4 component, and deploys the same way.
- **The v5 components are new, as `sst.aws.v5.*`.** A v5 component has the same type as the one it replaces, `sst:aws:Queue` for both queues. So when you switch one, what you've deployed is kept, what links to it sees no change, `Resource.MyQueue.type` stays the same, and a `$transform` for either applies to both.
- **20 components are ported:** `Alb`, `ApiGatewayV2`, `AppSync`, `Aurora`, `Bucket`, `Bus`, `Cluster`, `CognitoUserPool`, `CronV2`, `Dsql`, `Dynamo`, `Efs`, `Function`, `Mysql`, `Postgres`, `Queue`, `Redis`, `Service`, `SnsTopic` and `Task`.
- **The rest aren't ported yet**, like the sites (`Nextjs`, `Astro`, `StaticSite` and the others), `Vpc`, `Router` and `Cdn`. Keep using their v4 components. An app can mix the two.

---

## Before you install

1. **Update to the latest v4 and deploy.** Then the changes v4 made since your version are deployed on their own, and not with the move.

2. **Use Node.js 22 or later.**

3. **Check your `sst.config.ts`** for the four things v5 reads differently. Most apps have none of them.

   - **A `version` rule has to allow 5.x.** An app without one runs with any version.

     ```ts title="sst.config.ts" del={5} ins={6}
     export default $config({
       app(input) {
         return {
           name: "my-app",
           version: "4.x",
           version: ">= 4",
         };
       },
     });
     ```

     | Rule | v4 | `5.0.0-alpha.1` | `5.0.0-alpha.2` and later |
     | --- | --- | --- | --- |
     | No `version` | ✓ | ✓ | ✓ |
     | `"4.x"` or `"^4"` | ✓ | | |
     | `">= 4"` | ✓ | | ✓ |
     | `"5.x"` | | | ✓ |
     | `">= 5.0.0-0"` | | ✓ | ✓ |

   - **A provider pinned to a version** has to be in the major version SST's components are built for, like `aws` `7.x`. A newer major version is refused too now, and the error gives the versions to use.

   - **A file that re-exports a global by name**, like `export { aws }`, no longer builds. `export const x = aws` and `export default aws` work.

   - **A file that `app()` imports can't use a provider while it loads.** Providers aren't installed yet when `app()` runs, so a provider there is a stub that throws when it's used.

## Install v5

In your app:

```bash frame="none"
npm install sst@npm:@sst-community/sst@next-experimental
```

Or, for an app that isn't JavaScript, install the CLI globally. This replaces a global v4 CLI.

```bash frame="none"
curl -fsSL https://raw.githubusercontent.com/sst-community/sst/main/install | VERSION=5.0.0-alpha.2 bash
```

Then run `sst diff` on your stage. With your config as it was, the move itself shouldn't change anything.

```bash frame="none"
sst diff --stage <stage>
```

## Switch a component

1. **Read its "Switch from" section.** Every v5 component's page has one, with what's written differently. The [list below](#component-by-component) sums them up.

2. **Change the class and keep the name.**

   ```ts title="sst.config.ts" del={1} ins={2}
   const queue = new sst.aws.Queue("MyQueue");
   const queue = new sst.aws.v5.Queue("MyQueue");
   ```

3. **Make the changes the section lists.**

4. **Run `sst diff`.** Expect updates in place. If something that holds data is replaced or deleted, stop and check the section again.

5. **Deploy.**

Some components are taken by others. Switch the ones that take them first, or in the same deploy:

- The services on an `Alb`.
- The services and tasks in a `Cluster`.
- The functions, services and tasks that mount an `Efs`.

A v5 component takes either version of these, but a v4 one only takes the v4 version.

### What every v5 component does differently

- **Args that decide what gets created are plain values, not outputs.** Their types don't take an output, and one passed anyway is refused when your config runs, with the arg's name.
- **An object in `transform` is merged in**, nested objects too. In v4 it replaced the nested object it named. To replace one, use a function.

  ```ts title="sst.config.ts"
  transform: {
    // v4 replaced every variable, v5 adds A
    function: { environment: { variables: { A: "1" } } },
  }
  ```

- **`nodes` has every resource the component creates**, and each is the resource itself, not an output of it.
- **A resource you already have goes in `existing`.** For example, a function's `role` becomes `existing: { role }`, and a service's `taskRole` becomes `existing: { taskRole }`.
- **What only wires resources together is part of its parent.** A subscriber, a data source or an identity provider is no longer a component of its own, so its `transform` moves to the parent's `transform`, and its resources are in the parent's `nodes`.
- **Static methods that took the ARN of a resource outside your app are gone.** Look the resource up with `get`, and call the method on what `get` returns.

  ```ts title="sst.config.ts" del={1} ins={2}
  sst.aws.Bus.subscribe("MySubscriber", busArn, "src/subscriber.handler");
  sst.aws.v5.Bus.get("Shared", "my-shared-bus").subscribe("MySubscriber", "src/subscriber.handler");
  ```

- **If you set `tags` with an object in `transform`**, the tags SST sets are kept next to yours, and added back when you switch.
- **The functions a v5 component creates are `sst.aws.v5.Function`s.** You can keep writing their definitions the way `sst.aws.Function` takes them.

### What a switch can replace

Most switches only update resources in place. These are the exceptions:

- **A function whose part has a new name uploads its code again.** The function is updated in place. `CronV2`'s function is one: it was `MyCronJobHandler` and is `MyCronJobFunction`.
- **Nothing is replaced for a change of provider alone.** v4 created some resources with your app's provider, whatever the component was given: a durable function's URL alias, `AppSync`'s Lambda data sources and domain association, and the queue subscribers of a `Bus` or an `SnsTopic`. And what it added to a resource you looked up with `get` and a `provider` didn't get that provider: a `Bucket`'s notifications, a `Dynamo` table's subscribers, a `CognitoUserPool`'s clients. A v5 component gives each of them its own `provider`, and the switch keeps them, updated in place with that provider's default tags. A client keeps its ID.
- **A subscriber without a name isn't kept.** On a `Dynamo` table or an `SnsTopic`, every subscriber needs a name. Remove an unnamed one and deploy before you switch, then add it back with a name.

A `Service` also lists what `sst dev` runs for each container as removed and created again. That's only in your state; nothing changes in AWS.

## Component by component

The links go to each component's page, where its "Switch from" section has the details.

| Component | What to change |
| --- | --- |
| [`Alb`](/docs/component/aws/v5/alb/) | Switch its services first. `nodes.listeners` is `nodes.listener`. |
| [`ApiGatewayV2`](/docs/component/aws/v5/apigateway-http/) | Becomes `sst.aws.v5.ApiGatewayHttp`, named for the HTTP API it creates. A route's `transform` moves to the API's. `domain.nameId` becomes `existing: { domainName }`. `domain` is plain. |
| [`AppSync`](/docs/component/aws/v5/app-sync/) | The `transform` of a data source, function or resolver moves to the API's. `domain` is plain. With a `provider`, see [above](#what-a-switch-can-replace). |
| [`Aurora`](/docs/component/aws/v5/aurora/) | `replicas`, `proxy` and its `credentials` are plain. The master user's secret is `nodes.secret`. `transform.replica` changes only the replicas. |
| [`Bucket`](/docs/component/aws/v5/bucket/) | `public: true` becomes `access: "public"`. `subscribe`, `subscribeQueue` and `subscribeTopic` become `notify`. `versioning`, `cors` and `lifecycle` are plain. |
| [`Bus`](/docs/component/aws/v5/bus/) | The static `subscribe` and `subscribeQueue` become `get(...)` and then the method. A subscriber's `transform` moves to the bus's. |
| [`Cluster`](/docs/component/aws/v5/cluster/) | Switch its services and tasks first. `addService` and `addTask` are gone. `Cluster.v1` has no v5 form. |
| [`CognitoUserPool`](/docs/component/aws/v5/cognito-user-pool/) | An identity provider's `transform` becomes `transform.identityProvider`. `domain` and `triggers` are plain. |
| [`CronV2`](/docs/component/aws/v5/cron/) | Becomes `sst.aws.v5.Cron`, without the version: the first `Cron` has no v5 form. `job` becomes `function`, and `nodes.job` becomes `nodes.function`. |
| [`Dsql`](/docs/component/aws/v5/dsql/) | `regions.peer` is plain. `transform.peerBackupVault` changes only the peer's vault. |
| [`Dynamo`](/docs/component/aws/v5/dynamo/) | Every subscriber needs a name. The static `subscribe` becomes `get(...).subscribe(...)`. A subscriber's resources are in the table's `nodes`. |
| [`Efs`](/docs/component/aws/v5/efs/) | Switch what mounts it first. |
| [`Function`](/docs/component/aws/v5/function/) | `role` becomes `existing.role`, `logging.logGroup` becomes `existing.logGroup`, `live` becomes `dev` and `url.route` becomes `url.router`; the v4 forms still work. `dev`, `logging`, `url`, `python` and `concurrency` are plain. |
| [`Mysql`](/docs/component/aws/v5/mysql/) | `proxy` and its `credentials` are plain. The master user's secret is `nodes.secret`. |
| [`Postgres`](/docs/component/aws/v5/postgres/) | `proxy` and its `credentials` are plain. The master user's secret is `nodes.secret`. |
| [`Queue`](/docs/component/aws/v5/queue/) | Nothing. |
| [`Redis`](/docs/component/aws/v5/redis/) | Nothing. |
| [`Service`](/docs/component/aws/v5/service/) | `taskRole` and `executionRole` go in `existing`. `public` becomes `loadBalancer`, its `ports` become `rules`, and a rule's `path` becomes `conditions.path`. `loadBalancer`, `scaling` and `containers` are plain. |
| [`SnsTopic`](/docs/component/aws/v5/sns-topic/) | Every subscriber needs a name. With a `provider`, see [above](#what-a-switch-can-replace). |
| [`Task`](/docs/component/aws/v5/task/) | `taskRole` and `executionRole` go in `existing`. `containers` is plain. |

## If you wrote a package

A [package component](/docs/write-a-package-component/) built on the v5 alphas, up to `5.0.0-alpha.2`, works on 5.0 with a few changes. The rest of what it imports from `sst/components`, `sst/components/aws` and `sst/testing` is the same.

- **Two of SST's components have new names**, with the same type, so what an app deployed with them is kept:
  - `v5.ApiGatewayV2` is `v5.ApiGatewayHttp`, and its types are `ApiGatewayHttpArgs`, `ApiGatewayHttpAuthorizerArgs` and `ApiGatewayHttpRouteArgs`.
  - `v5.CronV2` is `v5.Cron`, and its args are `CronArgs`.
- **Two args are gone:** `Redis`'s `nodes`, which is `cluster.nodes`, and `Cluster`'s `forceUpgrade`.
- **`linkable` is gone** from `sst/components`. Use `Linkable.wrap`. `V5Args`, which wrapped a v4 component's args, is gone too.
- **Drop `skipLibCheck` and the `google-protobuf` pin.** SST's types check without `skipLibCheck`, under `moduleResolution: "bundler"` or `"NodeNext"`, and `mock()` works with the `google-protobuf` that `@pulumi/pulumi` installs.
- **`mock()` answers more as the cloud would.** An `Email`'s domain gets three DKIM tokens, so a test that gave them in `state` doesn't have to.

Then there's what a package can do now that it couldn't:

- **Read the app with `context()`**: its name, stage, removal and providers, whether it runs for `sst dev`, the command, and the stage's target.
- **Version a component**, so that renaming its parts moves an app's stage with `sst migrate` instead of replacing what's deployed. Give the component its next version with `takeover()`, and say where each part was.
- **Export a check**, made with `check()`, that an app turns on in `run()`. A deploy runs a preview first and stops on what the check finds.
- **Export a runtime**, made with `runtime()`, for a language SST doesn't build in, or **a target**, of the `Target` type, which `targetSuite()` from `sst/testing` tests.

Before 5.0 is released, SST's components move out of `v5`: `sst.aws.v5.Queue` becomes `sst.aws.Queue`, and `v5.Queue` from `sst/components/aws` becomes `Queue`. From 5.0 on, what a package builds on changes only in a major version.

## After you switch

Once your config uses `sst.aws.v5.*`, it doesn't run with a v4 CLI, which has no `sst.aws.v5`. Set a `version` rule, so that anyone on v4 is told their version doesn't match, before the config runs:

```ts title="sst.config.ts"
version: "5.x",
```

---

## Going back

**To switch a component back,** change `sst.aws.v5.X` back to `sst.aws.X`, and run `sst diff` before you deploy. A v5 component keeps some resources under new names, like a `Mysql`'s secret. The v4 component doesn't know those names, so it creates them again under its own, and deletes the v5 ones. Check that nothing that holds data is in that list. Switching back hasn't been tried in AWS yet.

**To go back to the v4 CLI,** switch every component back first. Then install the latest v4:

```bash frame="none"
npm install sst@npm:@sst-community/sst@latest
```
